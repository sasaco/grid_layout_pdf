調査日: 2026-10-16。対象: `.agents/docs/research/A4.pdf` の全 1 ページ。目的は実装計画の根拠収集であり、以下の測定値を文字配置仕様として確定したものではない。

## 検証方法と保存

- PDF の MediaBox、描画命令、文字情報を PyMuPDF で抽出した。
- 描画命令中の数値を Decimal で読み、浮動小数点抽出誤差を避けて格子間隔を確認した。
- 全ページを 144 dpi で PNG 化し、罫線のみの一様グリッドであることを目視した。
- Poppler は PATH と `C:/Users/sasai/.codex` 内から見つからなかったため、隔離した `uv --with pymupdf` 環境を使用した。製品依存の採用を意味しない。
- 調査前後 SHA-256 は同一: `eb6176ec32e60e494605da9e1e0481149eed89183d5ac306245db13ced603f60`。
- 再実行: `uv run --no-project --with pymupdf python tmp/pdfs/grid-reference/inspect_grid.py`。
- 測定スクリプト: `tmp/pdfs/grid-reference/inspect_grid.py`。生データ: `tmp/pdfs/grid-reference/measurements.json`。目視画像: `tmp/pdfs/grid-reference/A4-page-1.png`。

## 確認済み事実

以降の座標は特記しない限りページ左上原点、右向き x、下向き y、単位 pt とする。1 pt = 25.4 / 72 mm。

| 項目 | 実測値 | 備考 |
|---|---|---|
| ページ数 | 1 | ページ 1 を全体確認 |
| MediaBox / CropBox | `[0, 0, 595, 842]` | 約 209.903 × 297.039 mm。厳密な 210 × 297 mm ではない |
| 回転 | 0° | 左上基準への変換に回転補正は不要 |
| 縦罫線 | 31 本 | 30 列を形成 |
| 横罫線 | 48 本 | 47 行を形成 |

| 縦ピッチ | 15.48 pt | 5.461 mm、全間隔が一致 |
| 罫線の厚み | 0.96 pt | 約 0.338667 mm、すべて黒塗りの長方形 |
| 中心線グリッド原点 | `(50.88, 54.598)` | 最上・最左の罫線中心の交点 |
| 中心線グリッド右下 | `(533.28, 782.158)` | 中心線間の幅 482.4 pt、高さ 727.56 pt |

| 文字、ラベル、フォント | なし | 抽出 text.blocks と fonts はともに空。画像でも文字なし |

**30 × 47 の長方形セルからなるグリッドであり、正方形の 5 mm 方眼ではない。**

PDF の生ストリームは左下原点。最初の縦罫線は `50.4 59.362 .96 728.52 re f`、次の縦罫線は `66.48 59.362 .96 727.56 re f`。最上部の横罫線は `51.36 786.922 482.4 .96 re f`、次は `51.36 771.442 482.4 .96 re f`。中心座標への変換で上表の値が得られる。左端線だけが上辺まで延び、横線が左端線の内側端から始まるため、描画命令の長さをそのまま「グリッド領域」に使わず中心線基準と外縁基準を区別する。

## 数値モデル案（未確定）

PDF の実測を保持する `reference_exact` プロファイル案:

```text
page_size_pt = (595, 842)
origin_pt = (50.88, 54.598)       # outer grid-line center intersection
pitch_pt = (16.08, 15.48)
columns = 30
rows = 47
debug_line_width_pt = 0.96
x_boundary(c) = 50.88 + c * 16.08     # c = 0..30
y_boundary(r) = 54.598 + r * 15.48    # r = 0..47
```

これは PDF を再現する座標の一案であり、文字原点を罫線中心に置くという意味ではない。文字の配置原点、マス内余白、文字送り、基線は別の Typography / TextPlacement 設定とするのが妥当。正式な A4 サイズ 210 × 297 mm に合わせる場合は、ページだけ変更するかグリッドを再配置するかを明示する必要がある。参照値を無言で標準寸法や等間隔余白へ丸めない。

## 資料から決められない点

1. **1 マスに全角何文字を割り当てるか。** 文字がないため「大マス = 全角 1 文字」は導けない。半角 / 全角の送り比、任意の細分位置の使用可否も未確定。
2. 文字サイズ、フォント、CJK / 欧文 / 数字 / 記号それぞれの送り、添字・分数・根号の組み方。
3. グリッド線に対する基線 offset と、文字外接矩形をどこで揃えるか。行の上端・中心・下端と baseline は区別が必要。
4. 計算式の等号をグリフ左端・中心・送り枠のどれで揃えるか。等号位置は数式グループごとに設定するか、文書全体で固定するか。
5. 文字をグリッドへ合わせる操作の詳細。ユーザーの「文字サイズを維持して開始位置・送り・行位置を合わせる」方針を受けても、文字送りの変更許容値と禁則処理は別途定義する必要がある。
6. 全 47 行を本文に使うか、ヘッダー / フッターをこの領域内に確保するか。グリッドを完成 PDF に印刷するか、開発時のガイドに限るか。
7. 参照の非対称余白をそのまま標準にするか。A4 の物理寸法を厳密化するか。

## 計画・検証への含意

- グリッドの幾何とタイポグラフィの役割を分離し、等号の基準位置を数式部品の明示的な anchor として扱う。
- 「グリッドに収めるため文字サイズを自動縮小」を暗黙の解決策にしない。長文・長い式の折返し、行占有、溢れの報告を計画に含める。
- 30 列 × 47 行の格子再現試験と、文字・数式配置試験を別々に行う。後者の基準は A4.pdf 単独では作れず、`tests/output/*.pdf` とユーザーの配置規則を必要とする。
- 画像差分だけでは文字基線や等号位置の保証が弱い。レイアウト計算結果に grid row / column、基線、glyph x / y、equal anchor を出し、座標の数値検証と描画の目視を併用する。

以上は資料調査と設計上の論点であり、製品コード・製品 API の実装は行っていない。
